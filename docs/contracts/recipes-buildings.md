# Contract: recipes, buildings, construction, production orders (E12-E14)

Status: proposal by architect agent. Does not change code. Follows CLAUDE.md rules:
JSON via `Defs`, sim is `RefCounted` (no Node), all item create/destroy through `Ledger`,
deterministic (`sim.rng` only), player commands go through `Simulation` methods.

Existing decisions kept: buildings are walkable (colonists and enemies path through them);
workers stand on the top-left cell (`Building.cell`); wear/broken/repair exist
(`wear_per_batch`, `wear_per_shot`, `condition`, `broken`); one item stack per cell rule untouched.

## 1. Recipe schema (`data/recipes.json`)

| field | type | req | meaning |
|---|---|---|---|
| `name` | string | yes | display name |
| `inputs` | {item_id: int} | yes | consumed per batch (from building `input` buffer) |
| `outputs` | {item_id: int} | yes | produced per batch (into building `output` buffer) |
| `work_ticks` | int | yes | worker-ticks of work per batch at skill factor 1.0 |
| `building` | string | yes | building def id that may run this recipe (building also lists it in `recipes`) |
| `skill` | string | yes | `mining` / `construction` / `crafting` / `smelting` / `cooking` / `medicine` / `none` |
| `power_kw` | float | no | extra power draw while this recipe runs (default 0; adds to building `power_use_kw`) |

`skill_speed_factor`: progress per tick = `1.0 * skill_factor(colonist.skill_level) * power_satisfaction`.
The curve lives in `data/balance.json` (`skill_speed_factor` table level -> multiplier, e.g. 0.6 at L0, 1.0 at L5, 1.6 at L10);
it is not stored per recipe. Recipes with `skill: "none"` ignore it.

```json
{
	"refine_essence": {
		"name": "Очистка эссенции",
		"inputs": {"essence_ore": 10},
		"outputs": {"refined_essence": 3, "waste": 4},
		"work_ticks": 100,
		"building": "refinery",
		"skill": "smelting"
	},
	"smelt_plate": {
		"name": "Плавка пластины",
		"inputs": {"refined_essence": 2},
		"outputs": {"plate": 1},
		"work_ticks": 60,
		"building": "fabricator",
		"skill": "crafting",
		"power_kw": 0.5
	}
}
```

Validation (in `Defs` load, assert in tests): every item id exists in `items.json`; `building` exists and
lists the recipe id in its `recipes`; inputs/outputs non-empty counts > 0.

## 2. Building schema (`data/buildings.json`)

| field | type | default | meaning |
|---|---|---|---|
| `name`, `color` | string | - | display (kept) |
| `size` | [w,h] | - | footprint, top-left anchored (kept) |
| `max_hp` | int | - | (kept) |
| `cost` | {item: int} | {} | construction materials (also basis for deconstruct refund) |
| `buildable` | bool | true | false = scenario-only (e.g. `hq`) |
| `category` | enum | `structure` | `production` / `power` / `logistics` / `defense` / `structure` / `furniture` (build-menu tab) |
| `recipes` | [recipe_id] | [] | recipes this building can host; empty = not a machine |
| `input_capacity` | int | 0 | total items in input buffer (kept) |
| `output_capacity` | int | 0 | total items in output buffer (kept) |
| `wear_per_batch` | float | 0 | condition lost per finished batch (kept) |
| `wear_per_shot` | float | 0 | turrets (kept) |
| `power_use_kw` | float | 0 | continuous draw while operating (idle machines draw 0) |
| `power_gen_kw` | float | 0 | output of generators |
| `walkable` | bool | true | explicit; `false` reserved for walls/doors later (pathfinder must then block the cells) |
| `turret` | {range, damage, cooldown_ticks} | - | (kept) |
| `threat_priority` | int | 0 | enemy targeting weight (kept) |
| `shelter`, `critical` | bool | false | (kept) |
| `sprite` | string | `<id>.png` | file in `assets/sprites/` (generated by `tools/gen_art.py`) |
| `build_ticks` | int | 60 | construction work_ticks (see 3) |

Example:
```json
"refinery": {
	"name": "Установка", "size": [2,2], "color": "#b0446b", "max_hp": 250,
	"cost": {"essence_ore": 20}, "buildable": true, "category": "production",
	"recipes": ["refine_essence"], "input_capacity": 20, "output_capacity": 30,
	"wear_per_batch": 12, "power_use_kw": 1.0, "threat_priority": 3, "sprite": "refinery.png"
}
```

### Migration note: `recipe` -> `recipes`
Currently `refinery.recipe = "refine_essence"` (string) and `Building.recipe_id` / `Building.recipe` hold the
single active recipe. Change: JSON key becomes `recipes` (array). `Building` keeps `recipe_id` / `recipe` as the
*selected* recipe (default = `recipes[0]`; changed by `set_building_recipe`). `Defs` loader accepts legacy
singular `recipe` for one release (wraps to `[recipe]`) and logs a warning; remove after migrating the JSON.
`Building.is_machine()` becomes `not def.recipes.is_empty()`. Changing the selected recipe: input buffer items
that the new recipe does not use are spilled via `ItemSystem.drop()`; in-progress batch is discarded
and its inputs refunded to the buffer (no Ledger event because nothing is created/destroyed).

## 3. Construction: blueprints

Owner: `BuildingSystem` (`blueprints: Array[Blueprint]`, `Blueprint` = new `RefCounted` in `sim/buildings/blueprint.gd`).
A blueprint occupies the footprint cells (so no double placement; `occupancy` marks them with the blueprint id,
`BuildingSystem.at()` returns null for them) and is walkable.

Fields: `id`, `def_id`, `cell`, `state`, `delivered: Dictionary` (item->n, held inside the blueprint),
`work_done: int`, `deconstruct: bool`.

State machine:
```
planned --(first material reserved)--> delivering --(delivered >= cost)--> building
building --(work_done >= build_ticks)--> done  => Building created, Blueprint removed, building_completed
planned|delivering|building --cancel--> removed; delivered materials spilled back via ItemSystem.drop()
completed Building --deconstruct--> job removes it; refund floor(cost * refund_fraction) via drop(); rest destroyed
```
Cost-free blueprints skip `delivering`. A blueprint with no cost goes planned -> building directly.

Ledger: materials delivered into a blueprint are *moved* (not destroyed). When the building completes,
`delivered` cost is consumed: `ledger.destroy("construction", item, n)` (new reason `construction`). Cancel and
deconstruct refunds are moves via `drop()`; the non-refunded part is `ledger.destroy("deconstruct", ...)`.
Existing `place(def_id, c, pay)` stays for scenarios/tests (instant, pays directly) and for `hq`.

`balance.json`: `construction.refund_fraction` (default 0.5), `construction.cancel_refund_fraction` (default 1.0).

Jobs (new, in `sim/jobs/`, work-giver style, reservation keys `bp:<id>:haul:<item>` and `bp:<id>:build`):
- `HaulToBlueprintJob`: pick item stack in storage -> carry -> deliver to nearest blueprint cell; state `planned -> delivering`.
- `ConstructJob`: stand on blueprint top-left cell, add progress per tick (skill `construction`); when done call `BuildingSystem.complete_blueprint(bp)`.
- `DeconstructJob`: same as construct, reversed; at the end `BuildingSystem.finish_deconstruct(b)`.
Priorities in `data/jobs`/priorities JSON: haul-to-blueprint above plain hauling, construct above crafting, below flee/repair.

Bus signals (add to `autoload/event_bus.gd`):
`blueprint_placed(blueprint_id: int)`, `blueprint_cancelled(blueprint_id: int)`,
`building_completed(building_id: int)` (also fired for instant `place()` in addition to existing `building_placed`, or
`building_placed` is kept as the generic "exists now" signal and `building_completed` only for blueprints; decide in Q2),
`building_deconstructed(building_id: int)`. Existing: `building_placed`, `building_destroyed`, `building_broken`, `building_repaired`.

## 4. Production orders

Owner: `BuildingSystem` (orders are per-building state: `Building.orders: Array[Dictionary]`); keeps the dependency
direction simple. Split into `sim/production/` only if orders become cross-building (bills, global stock targets).

Order dictionary (plain, serialisable):
```
{ "id": int, "recipe": "smelt_plate", "mode": "count"|"maintain"|"forever",
  "n": int, "done": int, "paused": bool }
```
- `count` ("make N"): run N batches then remove the order. `done` increments per finished batch.
- `maintain` ("keep N in storage"): active only while `ItemSystem.count_in_storage(first output item) < n`.
- `forever`: run while inputs available (current behaviour of the refinery; the default order when none is set).
- Orders execute top to bottom; the first runnable one is active. A building with no orders and `recipes.size() == 1`
  behaves as `forever` of its only recipe (backward compatible).
- Inputs are still hauled by the existing haul-to-machine job; the haul job only hauls inputs for the *active* order's recipe.

Simulation commands (all validate, return `String` error or `""`/id, never poke internals from view):
- `place_blueprint(def_id: String, cell: Vector2i) -> int` (blueprint id or -1; error via `placement_error`)
- `cancel_blueprint(blueprint_id: int) -> bool`
- `deconstruct(building_id: int) -> bool` (creates a deconstruct designation; `hq` and `critical` refused)
- `set_building_recipe(building_id: int, recipe_id: String) -> bool`
- `set_production_order(building_id: int, order: Dictionary) -> int` (order id; pass `{"id": existing}` to edit,
  `n = 0` with mode `count` removes)
Each is a plain method on `Simulation` so replay/save can log (tick, command, args).

## 5. Power and logistics stubs (interface names only, do not build in E12-E14)

`sim/power/`: `PowerSystem` (RefCounted). `Generator` (reads `power_gen_kw`), `Pole`/`Wire` (grid connectivity by
adjacency radius), `Consumer` (reads `power_use_kw` + recipe `power_kw`). Per tick per grid:
`satisfaction = clamp(supply / demand, 0, 1)`; machine progress and turret cooldown scale by `satisfaction`
(shortage degrades speed proportionally, never stops entirely unless supply is 0). API: `PowerSystem.satisfaction_for(building_id) -> float`.
Bus: `power_changed(grid_id)`.

`sim/logistics/`: `LogisticsSystem`. `Conveyor` (cell-based, direction, moves one item per N ticks, goes through
`ItemSystem` stacks or own slot), `Inserter` (moves item between adjacent building buffer and conveyor/storage cell).
Interface: `LogisticsSystem.can_insert(building, item) -> bool`, `try_extract(building) -> Dictionary`.
Everything uses `Ledger` only for creation/destruction, never for moves.

## 6. Open questions for the orchestrator

1. Do blueprints block pathing? Proposal: no (walkable), consistent with buildings. Confirm.
2. `building_placed` vs `building_completed`: keep both (placed = exists, completed = finished via blueprint) or merge?
3. Should deconstruct require a worker on-site (job) or be instant refund? Proposal: job, `build_ticks / 2`.
4. Are orders per building (this doc) or global "bills" (RimWorld style, one list choosing any capable building)? Per building is simpler; global needs `sim/production/`.
5. Refund fraction for a *damaged* building: scale by `hp / max_hp`? Proposal: no, flat `refund_fraction`.
6. Which skills exist at E12 (progression stage)? Recipes reference skill ids now; if skills are not built yet, `skill_speed_factor` is 1.0 constant.
7. Power: do we ship `power_use_kw` fields in JSON at E12 as dead data, or add them only at the power stage?
