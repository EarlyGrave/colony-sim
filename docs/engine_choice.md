# Выбор движка: что делать, когда Godot станет тесен

Гайд для владельца проекта. Написан простым языком; каждый термин объясняется при первом упоминании, в конце есть глоссарий и чек-лист решений.
Дата: октябрь 2026. Факты про версии и цены меняются быстро — перед важным решением перепроверь по ссылкам в конце.

## 0. Коротко (TL;DR)

- Прямо сейчас **менять движок не нужно**. Игра играется на телефоне в браузере, симуляция уже отделена от картинки — это главный актив.
- Самая ценная инвестиция сегодня: сделать **ядро симуляции переносимым** («sim core as a portable library») и покрыть его **golden-replay тестами**. Тогда выбор движка превращается из «судьбоносного» в «заменяемую деталь».
- Два реалистичных пути: **A) остаться на Godot, а горячую часть симуляции со временем вынести в C++/Rust**; **B) Unity (C#, DOTS)** — если важнее Steam/мобильные магазины и огромная экосистема. Rust/Bevy — интересный, но рискованный третий путь.
- Решения «сейчас» и «потом» — в разделе 6.

## 1. Что вообще делает игровой движок

**Движок** (game engine) — набор готовых «кирпичей», чтобы не писать всё с нуля: показ графики, ввод (касания, мышь), звук, загрузка картинок, редактор сцен, экспорт на платформы (ПК, телефон, веб). Игровые правила (твоя колония, заражение, волны тварей) — это *твой* код поверх движка.

В нашей игре они уже разделены (см. `CLAUDE.md`): `sim/` — чистая симуляция без графики, `view/` — только показывает. Это очень удачно: **заменить нужно будет в основном `view/` и «клей», а не всю игру**.

### Что важно именно для НАШЕЙ игры

| Требование | Почему важно | Что это значит для движка |
|---|---|---|
| Большая детерминированная симуляция | Один seed + одни команды = одна и та же игра (сохранения повтором команд, реплеи, отладка) | Нужен контроль над порядком вычислений и числами; движок не должен «вмешиваться» в симуляцию |
| Много юнитов (сейчас 300 тварей, цель 1000+) | Скорость тика | Желательно компилируемый код и компактные данные в памяти, а не тысячи «объектов-узлов» |
| Логистика фабрики (ленты, автоматизация) | Тысячи предметов на лентах каждый тик | Тот же вопрос: данные плотно, цикл быстрый |
| Поиск пути (pathfinding) | Сейчас AStarGrid2D + компоненты связности | Своя реализация на сетке легко переносится в любой язык |
| Сохранения и реплеи | Уже сделаны повтором команд | Нужна стабильность: апдейт движка не должен менять результат симуляции |
| Моды | Хочется data-driven (JSON — уже так) | Данные в JSON переносятся бесплатно; скрипты-моды сложнее |
| Телефон / веб / ПК / Steam | Играем с телефона в браузере | Критично: **веб-экспорт** и **мобильный экспорт** |
| Пиксель-арт, псевдо-3D | Камера в перспективе, блоки, спрайты | Любой современный движок умеет; важно простое 2D/3D-смешение |
| Один хоббист + ИИ-ассистент пишет код | Скорость итераций, качество подсказок ИИ | Популярный язык, много открытого кода, текстовые (не бинарные) файлы проекта |

Главный вывод: **узкое место — это симуляция (CPU), а не графика**. Поэтому вопрос «какой движок» на 70% превращается в вопрос «на каком языке и в каком формате данных живёт симуляция».

## 2. Термины, которые встретятся дальше

- **GDScript** — язык Godot, похож на Python. Интерпретируется (выполняется «на лету»), поэтому медленнее компилируемых языков.
- **C++ / Rust / C#** — компилируемые языки. C++ и Rust быстрые, работают с памятью напрямую; Rust строже и безопаснее, C# попроще, но с «сборщиком мусора» (GC) — автоматической уборкой памяти, которая иногда вызывает микрофризы.
- **GDExtension** — способ подключить к Godot свой код на C++/Rust (как библиотеку), не пересобирая сам движок.
- **ECS** (Entity Component System) — стиль организации данных: «сущность» — просто номер, «компоненты» — данные в плотных массивах, «системы» — циклы по этим массивам. Из-за плотной памяти быстро для тысяч одинаковых юнитов. Противоположность — «объекты с методами» (ООП/узлы).
- **DOTS** — набор технологий Unity для ECS + Burst (быстрый компилятор) + Jobs (многопоточность).
- **WASM / WebAssembly** — формат, в котором скомпилированный код запускается в браузере почти с нативной скоростью (обычно в 1.5–3 раза медленнее нативной).
- **WebGL / WebGPU** — способы рисовать на видеокарте из браузера. WebGL старый и повсеместный, WebGPU новее и мощнее.
- **Детерминизм** — одинаковый вход всегда даёт одинаковый результат. Враги детерминизма: числа с плавающей точкой на разных платформах, порядок обхода словарей, многопоточность, время.
- **Golden replay** — «эталонная запись»: сохранённая последовательность команд + контрольная сумма состояния игры. Тест прогоняет запись и сверяет сумму. Подробно в разделе 5.
- **Single-threaded web** — наш веб-экспорт идёт в один поток (без `SharedArrayBuffer`), чтобы GitHub Pages работал без особых заголовков.

## 3. Сравнение кандидатов

Для каждого: плюсы/минусы для нас, кривая обучения, 1000+ агентов, веб/мобильные, лицензия, помощь ИИ, цена переноса.

### 3.1 Godot 4 (то, что у нас сейчас)
- **Язык:** GDScript; плюс C++ через GDExtension; плюс C# (отдельная сборка .NET). Мы на GDScript специально — из-за веба.
- **Плюсы:** бесплатный, открытый (лицензия MIT — никаких отчислений навсегда), лёгкий, быстрый цикл разработки, веб-экспорт работает (мы уже на Pages), текстовые файлы сцен — ИИ хорошо правит.
- **Минусы:** **C# в веб-экспорте Godot 4 не поддерживается** (по состоянию на 4.5; к 4.7 я не нашёл официального подтверждения — считай «нет или экспериментально»). GDScript медленнее: для 1000+ агентов и тысяч предметов на лентах упрёмся в потолок. Встроенного ECS нет. Веб-сборка с GDExtension возможна, но сложнее (нужна пересборка под Emscripten) — тема на форуме Godot, проверять отдельно.
- **Кривая обучения:** самая пологая из всех. Ты уже в ней.
- **1000+ агентов:** в GDScript — на грани (наш бенч: 300 тварей = 1.5 мс/тик на десктопе, в вебе ×2–3). С ядром на C++/Rust — комфортно.
- **Веб/мобильные:** веб — да (одно-поточный, как у нас), Android/iOS — да.
- **Лицензия:** MIT, 0 ₽. Steam — экспорт на ПК есть, интеграция Steamworks через плагин (GodotSteam).
- **ИИ-ассистент:** хорошо знает GDScript, но реже, чем C#/Python/C++; бывает путает Godot 3 и 4 — наши тесты это страхуют.
- **Перенос из текущего:** 0 (мы здесь). Добавить C++/Rust-ядро — средне (недели).

### 3.2 Unity (C#)
- **Плюсы:** огромная экосистема и обучающие материалы, C# хорошо знают ИИ-ассистенты, зрелые мобильные сборки и интеграции (Steam, магазины), **DOTS/ECS + Burst** дают сотни тысяч агентов — по производительности лучший «готовый» вариант из больших движков. Unity 6 поддерживает веб-платформу (WebGL/WebAssembly).
- **Минусы:** закрытый код; **история с лицензиями**: в 2023 анонсировали плату за каждую установку (Runtime Fee), в сентябре 2024 её отменили, вернулись к подписке на место ([источник](https://unity.com/runtime-fee)). Доверие подорвано, условия могут снова поменяться. Personal бесплатен до порога дохода/финансирования (после отмены fee — около $200 тыс.), Pro — порядка $2 тыс. за место в год (по сторонним обзорам; сверяй на unity.com). DOTS сложнее для новичка, API часто менялся; веб-сборка тяжёлая (десятки МБ), DOTS в вебе ограничен отсутствием потоков — нужно проверять.
- **Кривая обучения:** средняя, DOTS — крутая.
- **1000+ агентов:** отлично с DOTS; без DOTS (обычные MonoBehaviour) — терпимо до нескольких тысяч.
- **Веб/мобильные:** веб — есть, но «тяжёлее» Godot, мобильный браузер — слабое место; Android/iOS — отлично.
- **Детерминизм:** float в Burst можно настроить, но детерминизм между платформами нужно специально проектировать (фикс-пойнт или целые).
- **Перенос:** GDScript → C#: переписать всё `sim/` (~вручную с ИИ, но тесты помогут). Средне-тяжело. Сцены/картинки/JSON-данные переиспользуются.

### 3.3 Unreal Engine 5 (C++, Mass)
- **Плюсы:** топовая 3D-графика, C++, есть Mass Entity (ECS-фреймворк для больших толп).
- **Минусы:** для 2D-пиксель-арта и телефона — избыточен и тяжёл; редактор требует мощного ПК (в облачной сессии не запустить); **официального веб-экспорта в UE5 нет** (HTML5 вынесли в сообщество, там почти нет активности; остаются Pixel Streaming — видеопоток с сервера, платно по трафику/серверам) ([источник](https://forums.unrealengine.com/t/html5-support/1172997)). Лицензия: бесплатно до $1 млн дохода, затем роялти 5% (условия бери с сайта Epic, я их здесь не перепроверял).
- **Кривая обучения:** крутая. ИИ помогает хуже: огромный API, часто устаревший код, бинарные ассеты (.uasset) не читаются текстом.
- **Вердикт:** для нашей игры не подходит. Исключаем.

### 3.4 Bevy (Rust, ECS)
- **Плюсы:** ECS — основа движка, как раз под «много агентов»; Rust — быстрый и безопасный; всё текстом в коде, никаких бинарных сцен — ИИ работает естественно; лицензия MIT/Apache-2.0; веб через WASM + WebGL2/WebGPU (рендер на `wgpu`) работает; на Rust можно делать детерминированное ядро.
- **Минусы:** движок **до версии 1.0**, каждые ~3–4 месяца выходят релизы с ломающими изменениями (0.17 осенью 2025, 0.18 — по сторонним данным, весной 2026) ([источник](https://gamefromscratch.com/bevy-0-17-released/)). **Нет встроенного визуального редактора** сцен. Rust: долгая компиляция, строгий компилятор (ИИ часто ошибается с заимствованием — «borrow checker», но компилятор подсказывает и итерации сходятся). Мобильные сборки возможны, но менее обкатаны. UI для тач-интерфейсов — слабое место.
- **Кривая обучения:** крутая (Rust + ECS-мышление).
- **1000+ агентов:** отлично.
- **Перенос:** полный рерайт и `sim/`, и `view/`, и UI. Тяжело (месяцы хобби-времени), но ядро на Rust потом переиспользуется где угодно.

### 3.5 Свой движок (C++/Rust + SDL / raylib / sokol) — путь Factorio
- **Что это:** берём лёгкую библиотеку для окна/ввода/рисования (**SDL**, **raylib** — обе с разрешительными лицензиями zlib; **sokol** — тоже) и пишем остальное сами. Factorio написан на собственном C++ движке, поэтому у неё такая сумасшедшая производительность и детерминизм (мультиплеер и реплеи на нём держатся).
- **Плюсы:** полный контроль над детерминизмом, памятью, форматом сохранений; веб через Emscripten (raylib, sokol и SDL умеют); нет чужих лицензий и ломающих обновлений.
- **Минусы:** нет редактора, UI, анимаций, звука «из коробки» — всё сам. Для хоббиста с ИИ это огромный объём «обвязки», не связанной с геймплеем. Тач-UI, шрифты, кириллица, аудио, публикация — всё на нас. Именно здесь ИИ полезен (C++/Rust он знает хорошо), но отладка графических багов без GUI в облаке — боль.
- **Перенос:** рерайт `view/` целиком; sim — как порт.
- **Вердикт:** разумно только как **гибрид**: ядро симуляции свое, а презентация — в готовом движке (см. путь A).

### 3.6 MonoGame / FNA (C#)
- Фреймворки (не полные движки) для 2D/3D, наследники XNA. MonoGame — MIT; FNA — Ms-PL, упор на точную совместимость. Многие хиты сделаны на них (Stardew Valley, Celeste — на XNA/FNA-линии).
- Плюсы: C#, свой контроль над циклом симуляции, лёгкие. Минусы: нет редактора; **веб-экспорт слабый/экспериментальный** (через WASM и сторонние порты, на телефоне в браузере — риск); для нас это «своё решение с C#».
- Подходит, если откажемся от веба. Сейчас веб — наш козырь, так что не приоритет.

### 3.7 Defold и другие — коротко
- **Defold:** бесплатный, исходники открыты (но лицензия не OSI: «Defold License»), язык Lua, **очень лёгкий веб/мобильный экспорт** (сборка в сотни КБ), сильное 2D. Для 3D-псевдо-вида и большой симуляции Lua медленнее, нативные расширения на C++ есть. Хороший кандидат, если приоритет — веб/телефон; меньше сообщество и знаний у ИИ.
- **Cocos, Phaser (JS/TS, чисто веб), Love2D (Lua):** для веба проще всего, но JS/Lua на 1000+ агентов с фабрикой — потолок ближе.
- **Unity/Godot-подобные «гибриды»** (Flax, Stride, O3DE) — ниша, ИИ знает их плохо. Не рекомендую.

## 4. Два (с половиной) реалистичных пути

### Путь A. «Остаёмся на Godot, горячую симуляцию выносим в C++/Rust-ядро»
1. Сейчас: всё как есть, плюс готовим ядро к переносу (раздел 5).
2. Когда упрёмся в тик > ~10 мс на телефоне или 1000+ агентов: самые тяжёлые куски (`threats`, ленты/логистика, поиск пути) переписываем на Rust или C++ и подключаем через **GDExtension**. GDScript остаётся «клеем» и UI.
3. Веб: GDExtension под WASM — возможен, но требует отдельной сборки и проверки; **это главный риск пути**, его надо проверить маленьким прототипом заранее (1 день).
- **Плюсы:** ничего не выбрасываем, итерации быстрые, лицензия MIT, веб остаётся.
- **Минусы:** два языка в проекте, тоньше граница «ядро ↔ Godot» (копирование данных между ними), риск веб-сборки.
- **Подходит, если:** главное — телефон/веб и быстро получать играбельные версии.

### Путь B. «Переезд на Unity с DOTS»
1. Переносим ядро симуляции в C# (структуры + Burst-jobs), UI и камеру делаем заново.
2. Выигрыш: производительность в тысячи юнитов «из коробки», мобильные магазины, Steam, куча готовых плагинов, ИИ очень уверенно пишет C#.
- **Минусы:** зависимость от политики Unity (история Runtime Fee), тяжёлый веб, DOTS сложен и меняется, детерминизм надо проектировать, редактор не запустить в облачной сессии без GUI так же свободно, как Godot headless (есть batch mode, но тяжелее).
- **Подходит, если:** цель — коммерческий релиз в Steam/магазинах и большая экосистема важнее веба.

### Путь C (на будущее). «Rust/Bevy целиком»
Максимальная производительность и контроль, но полный рерайт и незрелый движок (до 1.0, ломающие релизы). Выбирать, только если ты готов(а) учить Rust и переживать апдейты. Разумная промежуточная форма: **ядро на Rust (общее для A и C)**, а презентация — в Godot сегодня и, при желании, в Bevy завтра.

**Мой совет:** путь A, с мини-прототипом «Rust-ядро + GDExtension + веб-сборка», когда симуляция реально начнёт тормозить. Путь B — только если решишь, что веб не нужен и цель — Steam/магазины.

## 5. «Ядро симуляции как переносимая библиотека»

Идея: `sim/` — это *продукт*, а движок — *оболочка*. Ядро:
- не знает про сцены, узлы, картинки, время, глобальные синглтоны (у нас это уже правило из `CLAUDE.md`);
- принимает **команды** (`designate_mine`, `place_building`…) и **тик** (`step()`), отдаёт **состояние** и **события**;
- хранит данные в плотных структурах (массивы чисел, целочисленные id), а не в графах объектов;
- использует только целую арифметику или строго контролируемые числа (избегаем различий float между платформами), свой генератор случайных чисел (`sim.rng` — уже так);
- читает баланс из JSON (`data/*.json`) — эти файлы переиспользуются в любом движке.

### Golden replay тесты
1. Записываем «золотую» игру: seed + список команд по тикам (у нас сохранения и так повтором команд).
2. Каждые N тиков считаем **хеш состояния** (контрольную сумму: позиции, склады, заражение) и сохраняем рядом.
3. Тест воспроизводит запись на новой реализации и сверяет хеши. Совпало — порт верный; разошлось — тест показывает *первый* тик, где расхождение.
4. Держим несколько записей: мирная игра, налёт, конец колонии, 250×250 с 300 тварями.

Почему это важно именно тебе: ИИ-ассистент может переписать систему на Rust/C#, а ты **доверяешь результату не на слово, а по тестам**. Это самая надёжная страховка при смене языка или движка. Нужно заранее решить: хеш должен быть описан спецификацией (какие поля, в каком порядке, как округляем), иначе разные языки дадут разные суммы.

Практические шаги (без смены движка, недели):
1. Ввести `Simulation.state_hash()` и 3–4 golden-записи в `tests/`.
2. Зафиксировать формат команд и событий (в `docs/` — спецификация-«контракт»).
3. Постепенно убирать из `sim/` GDScript-специфику: `Vector2i`, `Dictionary` с неупорядоченным обходом, `RefCounted` с сигналами — заменять на простые структуры.
4. Прототип: одна небольшая подсистема (например, поиск пути) на Rust, прогон тех же golden-тестов.

## 7. Глоссарий

- **Движок** — набор готовых блоков для игры (графика, ввод, звук, экспорт).
- **ECS** — стиль хранения: сущности-номера + компоненты-данные + системы-циклы.
- **DOTS** — ECS+Burst+Jobs в Unity.
- **GDExtension** — подключение C++/Rust к Godot без пересборки движка.
- **WASM** — код в браузере почти с нативной скоростью.
- **WebGL / WebGPU** — графика в браузере (старая/новая).
- **GC** — сборщик мусора, автоматическая уборка памяти (возможны микрозависания).
- **Детерминизм** — один вход → один результат всегда.
- **Golden replay** — эталонная запись игры для сверки порта.
- **Хеш состояния** — короткая «отпечаток-сумма» всего состояния игры.
- **Тик** — один шаг симуляции.
- **Headless** — запуск без окна/GUI (как наши тесты).
- **Роялти** — процент с выручки в пользу автора движка.
- **Emscripten** — компилятор C/C++ в WASM.
